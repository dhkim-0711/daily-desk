# 임시 저장·재개 규약 v1 — 2026-10-12 승인

이 문서는 EDITORIAL_GUIDELINES.md와 GENERATION_CONTRACT.md를 보완한다. 기사 선정·시의성·원문 검증·최근 14일 중복 검사·최종 JSON 규약을 완화하지 않는다. 마감 전 확정 금지와 조사 결과를 저장하지 않고 종료하는 동작을 분리한다. 최종 원고에는 새 필드를 추가하지 않는다.

## 역할·경로·예약

- 임시 조사본: `briefings/drafts/YYYY-MM-DD.json`. 원고 생성 작업만 작성하며 발송·제작 입력이 아니다.
- 확정 원고: 기존 `briefings/ready/YYYY-MM-DD.json`. 마감 후 전체 검증을 마친 경우에만 작성한다.
- `briefings/state`와 `briefings/rendered`는 이 기능에서 쓰거나 지우지 않는다. 발송 잠금과 확정본 우선순위를 유지한다.
- 기사 공개 마감은 09:30 KST. 원고 예약은 09:40, 기존 보충은 10:30·11:30. 첫 발송 목표 09:50과 발송 보충은 변경하지 않는다. 예약 시각이 아니라 실제 시각으로 마감 전후를 판단한다.
- 임시본 파일의 존재나 검사 통과는 기사 조사 완료·확정·제작·발송 완료가 아니다. 임시본을 ready 경로에 복사하거나 status만 바꿔 확정하지 않는다.
- 기존 제작 workflow의 ready 경로 필터와 제작기·발송기의 입력 경로는 그대로 둔다. drafts 저장만으로 제작·발송을 호출하지 않는다. 임시본은 웹사이트 메뉴·Moa·메일·PDF 본문에 표시하지 않는다. 저장소가 공개이면 임시본도 공개 파일이므로 비공개 메모나 개인정보를 넣지 않는다.

## 매 실행 시작

1. 현재 한국 날짜와 시각을 확인하고 세 규약을 읽는다. GitHub main의 당일 state와 ready를 먼저 읽는다. sending/sent/uncertain 또는 발송 시도 여부가 불명확하면 조사본·확정본을 변경하지 않는다. 상태 조회 오류를 파일 없음으로 처리하지 않는다.
2. ready가 있으면 기존 규약대로 본문과 현재 검증기로 검사한다. 유효하면 임시본보다 우선하며 종료한다. 파일 존재/status만으로 유효 판정하지 않는다. 무효 ready는 발송 시도 기록이 없음을 확인한 뒤 기존 보완 규약으로 처리하며, 임시본으로 덮어쓰지 않는다.
3. 최신 체크아웃에서 `python mail/drafts.py inspect --date YYYY-MM-DD`와 `python mail/candidates.py --date YYYY-MM-DD`를 실행한다. candidates의 draft_resume에는 당일 임시본과 단계가 포함된다. 실행 환경이 없으면 GitHub에서 같은 파일을 직접 읽고 아래 규약을 동일하게 적용한다.
4. 당일 drafts가 있으면 전체 내용과 실제 blob SHA를 읽어 재개한다. 잘못된 JSON·스키마·날짜·시각·조회 실패는 오류이며 빈 임시본이나 후보 없음으로 치환하지 않는다. 이전 날짜 임시본은 재개·자동 이월하지 않는다.

## 09:30 이전 실행: 조사하고 임시 저장

09:30 전이라는 이유만으로 아무것도 저장하지 않고 즉시 종료하지 않는다. 당일 아카이브·수집 상태·이력을 읽고, 현재 확인할 수 있는 후보와 공개 원문을 조사한다. 확인한 사실·출처·작성한 부분·미완료 항목을 구분해 임시본에 보존한다. 충분한 조사를 하지 못했으면 실제 수행 범위와 남은 확인 사항만 기록하고 완료를 만들지 않는다. 기사 4건 미만이나 빈 부분 원고도 임시본으로는 허용한다.

마감 전에는 확정본을 쓰지 않는다. 임시 저장 후 실제 현재 시각을 다시 확인한다. 같은 실행이 이미 09:30을 넘겼다면 바로 아래 마감 후 절차를 이어서 수행할 수 있다. 여전히 09:30 이전이면 임시본 저장 성공을 확인하고 종료하며, 다음 기존 마감 후 원고 실행이 이를 다시 읽는다. 실행 중 sleep·바쁜 대기·임의 추가 예약을 만들지 않는다. 이 기능은 종료한 실행을 스스로 깨우는 타이머가 아니다.

## 임시 JSON

정확한 최상위 필드:
- draft_schema_version: 정수 1. 최종 원고의 schema_version과 구별한다.
- status: draft.
- deliverable: false.
- date: 해당 한국 날짜 YYYY-MM-DD.
- cutoff_at: 당일 09:30 KST. 보충 실행·저장시각과 무관하게 고정한다.
- window_start: cutoff_at의 정확히 24시간 전.
- created_at: 실제 임시본 최초 작성시각. 갱신해도 보존한다.
- updated_at: 실제 이번 임시본 작성시각. 미래·소급 시각을 만들지 않는다.
- requires_post_cutoff_review: true. 마감 전 조사 기록이 있어도 확정 전 재점검이 필수다.
- research: 아래 다섯 배열만 포함하는 객체.

research의 다섯 배열:
1. candidates: 실제 후보 제목·원래 URL·수집/발행시각·확인된 사건 정보 등 공개 근거. RSS 메타데이터만 확인한 후보를 본문 검증 완료로 표시하지 않는다.
2. partial_articles: 실제 작성한 기사 부분 원고. 부족한 필드는 부족한 채로 두며, 허위 출처·시각·수치로 채우지 않는다.
3. partial_summary_groups: 작성된 부분 요약. 최종 기사번호와 완전성은 확정 단계에서 다시 검사한다.
4. review_records: 실제 검색식·기관 URL·본문 확인 결과·확인시각·접근 실패·이력 대조 결과 등 공개 가능한 작업 근거. 상세 사고 과정·개인 메모가 아니라 객관적인 진행 기록만 쓴다.
5. pending_checks: 아직 수행하지 않은 확인 사항을 문자열로 기록한다. 마감 전 임시본에는 마감 후 아카이브/수집기록 갱신, 다섯 영역 최종 보완 검색, 최신 14일 이력 및 원문 검증, 확정본 검사를 남긴다.

원문 전문·인증정보·이메일 주소·비공개 평가표·개별 점수·HTML·MIME·PDF는 넣지 않는다. 임시 스키마 검사는 구조·시각·일부 민감정보 패턴을 검사할 뿐, 내용 사실성이나 모든 개인정보의 부재를 보증하지 않는다. 저장 전에 작성자가 공개 가능성을 확인한다.

실행 환경이 있으면 research 객체를 로컬 파일로 작성한 뒤 다음을 사용한다. stdout은 로컬 임시 파일에 받아 전체 내용을 검사한다. 이 도구 자체는 GitHub·ready·state·rendered 파일을 쓰지 않는다.

```
python mail/drafts.py build --date YYYY-MM-DD --input /tmp/research.json > /tmp/draft.json
python mail/drafts.py validate --date YYYY-MM-DD --input /tmp/draft.json
```

--as-of는 모의 검사 전용이다. 실제 원고 작업에서는 생략하고 실제 시각을 사용한다.

## GitHub 임시 저장과 충돌

로컬 파일만 생성한 것을 GitHub 저장 성공이라고 보고하지 않는다. 저장 직전 main의 당일 state·ready·drafts를 다시 읽는다. 보호 상태나 유효 ready가 있으면 쓰지 않는다. 새 임시본은 create_file, 기존 임시본은 실제 최신 SHA를 사용한 update_file 한 번으로 전체 JSON을 저장한다. 응답의 성공과 저장 내용을 확인한다.

create 충돌·SHA 충돌은 다른 실행이 먼저 썼을 수 있다는 뜻이다. 최신 파일과 state·ready를 다시 읽고, 누락되지 않게 실제 확인한 기록을 병합한 뒤 재검사한다. 낡은 SHA 재시도·강제 덮어쓰기·파일 삭제로 충돌을 우회하지 않는다. 안전하게 병합할 수 없거나 접근/저장 오류가 지속되면 중단하고 원인을 보고한다. 보내기 함수는 호출하지 않는다.

## 09:30 이후 실행: 임시본 재개와 확정

1. 당일 임시본의 후보·부분 원고·공개 검증 기록·미완료 항목을 읽는다. 임시본이 없으면 정상 신규 조사를 시작한다. 임시본의 저장 시각을 수집/발행시각으로 바꾸지 않는다.
2. 최신 아카이브 전체(월별 parts 포함), 당일 collection과 최근 14일 실제 ready를 다시 읽는다. 임시본 이후 추가·수정된 기사와 수집 실패를 비교한다. 임시본은 이 갱신을 대신하지 않는다.
3. 마감 후 다섯 영역 보완 검색과 공식자료 확인을 매회 수행한다. 임시본에 reviewed/completed 기록이 있어도 이 단계를 생략하지 않는다. 누락된 마감 전 보도, 예정 회동의 실제 결과, 실증·수요처·정책·예산·사업화 현장 정보를 기존 지침으로 비교한다.
4. 최종 선정 기사 모두에 대해 공개 본문·사건 최초 공개일/실질적 새 사실·14일 사건 중복·수치/주장의 수준·09:30 공개 마감을 다시 확인한다. 이전에 확인한 사실과 출처는 재활용할 수 있지만 본문 수정·후속 사실과 근거 유효성을 대조한다. 실제 수집시각을 보존하고 늦은 수집에는 기존 cutoff_evidence를 기록한다. 마감 후 처음 공개된 사실은 이번 확정본에 넣지 않는다.
5. 최신 조사에 근거해 기존 최종 JSON을 완성한다. 임시 스키마/진행 기록을 최종 JSON에 통째로 넣지 않는다. 최종 created_at은 실제 확정 완료시각으로 새로 기록한다. 추가 조사·출처·선정 감사 기록의 완료 표시는 실제 수행 결과만 반영한다.
6. 최신 history를 포함한 체크아웃에서 `python mail/render.py --input /tmp/ready.json --validate-only`를 통과시킨다. 검증 실패·조사 미완료 시 ready에는 쓰지 않고, 발송 시도가 없고 유효 ready도 없으면 확인된 진행 내용을 임시본으로 보존한 뒤 사유를 보고한다. 스키마 검사만으로 원문 검증 완료를 주장하지 않는다.
7. 저장 직전 실제 시각이 09:30 이후이고 회차가 오늘인지, 당일 state·ready가 다른 실행에서 바뀌지 않았는지 재확인한다. 기존 최종 저장 규약에 따라 전체 ready를 단일 생성/갱신 호출로 저장한다. 임시본을 먼저 삭제하지 않는다. 확정본 저장이 실패하면 임시본을 보존해 재개 가능하게 한다.
8. 유효 ready 또는 발송 잠금이 생기면 남아 있는 임시본은 무시한다. 임시본은 계속 draft·deliverable=false이며 자동 삭제·재승격하지 않는다. 날짜가 바뀐 임시본은 당일 원고로 승격하지 않는다.
