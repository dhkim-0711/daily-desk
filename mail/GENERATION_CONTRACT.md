# 원고 저장 규약 v1

## 책임과 저장 순서

ChatGPT는 기사 선정·공개 본문 검증·분석 원고 작성만 담당합니다. 메일 발송, HTML 재설계, PDF 제작은 수행하지 않습니다. 메일 발송기는 `mail/templates/briefing.html.j2`의 고정 디자인을 사용합니다.

1. 한국 날짜를 결정하고 매회 그날 09:00을 마감 시각으로 고정합니다. 작업이 늦게 시작돼도 마감 시각을 이동하지 않습니다.
2. `briefings/state/YYYY-MM-DD.json`과 `briefings/ready/YYYY-MM-DD.json`을 확인합니다. 같은 날짜의 발송 시도 기록(sending/sent/uncertain)이 있으면 종료합니다. 기존 완성본이 있으면 전체 내용을 읽고 이 규약으로 검사하여 유효할 때만 종료합니다. 기존 파일이 잘못됐고 발송 시도 기록이 없으면 현재 GitHub 파일 SHA를 사용해 수정할 수 있습니다. 잘못된 기존 파일을 발견하고 수정하지 못하면 오류를 보고하며 완료라고 하지 않습니다. 사용자가 별도로 요청한 내용 수정은 별도 작업에서 처리합니다.
3. `mail/EDITORIAL_GUIDELINES.md`와 이 규약을 읽고, `docs/data/archive/index.json`과 해당 월(월경계면 두 달) 아카이브를 조사합니다.
4. 수집시각은 `firstSeenAt`, 보도시각은 `publishedAt`로 구분합니다. 수집 시각이 불명확하면 실제 마감 전 Git 커밋 등으로 입증합니다. 증거 없는 시각을 생성하지 않습니다. 09:00 이후 새로 수집·발표된 사실은 다음 날 대상으로 남깁니다.
5. 5개 독립 이슈를 원칙으로 공개 본문을 검증합니다. 충분히 조사했으나 적합한 이슈가 적으면 4개를 허용합니다. 4개 미만 또는 접근/검증 실패면 완성본을 만들지 말고 부족 사유를 작업 결과에 보고합니다. 제목·RSS 요약만으로 내용을 보충하지 않습니다.
6. JSON 전체를 작성·검사한 다음 **한 번의 GitHub 파일 생성**으로 저장합니다. 파일이 이미 생겼다면 읽고 종료하여 중복 쓰기를 피합니다. `status: ready`는 모든 검증을 마친 최종 원고에만 씁니다.
7. GitHub 저장 성공을 확인한 경우에만 원고 저장 완료라고 보고합니다. 발송 완료라고 보고하지 않습니다. 발송 결과는 별도 상태 파일과 Actions가 담당합니다.

## 파일 경로

- 완성 원고: `briefings/ready/YYYY-MM-DD.json`
- 전송 기록: `briefings/state/YYYY-MM-DD.json` (발송기만 작성)
- `ready/`에는 예제·중간본·부분 작성본을 저장하지 않습니다.
- JSON 데이터에는 이메일 주소, 인증정보, 개인 메모, 본문 전문 복제본을 포함하지 않습니다.

## JSON 필드

| 필드 | 형식·검증 기준 |
|---|---|
| schema_version | 정수 `1` |
| date | 한국 기준일 `YYYY-MM-DD` |
| cutoff_at | 해당 날짜 09:00의 시간대 포함 ISO 8601 |
| window_start | 마감 정확히 24시간 전의 시간대 포함 ISO 8601 |
| created_at | 실제 작성 완료 시각의 시간대 포함 ISO 8601, 마감 이후 |
| status | `ready` |
| summary_groups | `{article_numbers: [번호], bullets: [문장, 문장]}` 배열. 모든 기사 번호가 정확히 한 번씩 포함. 묶음별 제목은 주요 기사 제목에서 자동 생성 |
| articles | 4~5개 기사 배열 |

기사별 필드:

| 필드 | 형식·검증 기준 |
|---|---|
| number | 1부터 연속 정수 |
| title | 재검증된 수준의 한국어 표시 제목 |
| category | 실제 Daily Desk 수집 카테고리 |
| collected_at | 실제 수집 시각 ISO 8601, `(window_start, cutoff_at]` |
| original_published_at | 원 보도 최초 시각 또는 알려진 날짜만. 미래/마감 후 사실 금지 |
| original_url | 원래 수집 기사 URL, 가능한 경우 기록 |
| main_points | 확인된 사실 2~3개 문장 |
| implications | 기술·산업 파급·향후 전망과 연관된 국내 검토 방향 2~3개 문장 |
| sources | 직접 읽어 확인한 공개 본문 출처 1개 이상 |
| references | 외부 통계·순위·전망 등을 추가 인용한 경우에만 출처 배열. 없으면 생략 |

출처 필드:

| 필드 | 형식·검증 기준 |
|---|---|
| title | 실제 공개 원문 제목 |
| publisher | 매체·기업·기관명 |
| published_at | 실제 발행시각(시간대 포함 ISO) 또는 날짜 `YYYY-MM-DD`. 모르는 시간을 만들지 않음 |
| url | 직접 확인 가능한 HTTP(S) 원문 링크 |
| verification | `full_text`, `public_primary`, `public_reprint` 중 실제 확인 방법 |
| verified_at | 실제 본문 확인 시각, 작성 완료 시각 이전 |
| available_before_cutoff | 발행일만 알려진 당일 또는 전일 출처는 `true` 필요 (원 출처 현지 날짜와 KST 차이 반영) |
| cutoff_evidence | 위 경우 실제 마감 전 수집기록·Git 커밋·공개시각 확인 등 구체적 근거 |

참고자료는 `title`, `publisher`, `published_at`, `url`을 사용합니다. 날짜만 알려진 당일·전일 자료의 마감 전 이용 가능성도 증빙합니다. 예전 공식자료는 해당 이슈의 근거로 활용할 수 있지만 이전 사실을 당일 새 사실처럼 쓰지 않습니다.

`verification` 표시는 작성자의 검증 기록이며 프로그램이 본문 사실 자체를 검증했다는 뜻이 아닙니다. URL·날짜·필수 필드 검사는 최소 요건입니다. 실제 본문 접근과 숫자·주장·시험조건 구분은 작성자가 책임지고 확인합니다.

## 내용 작성

`main_points`, `implications`, `bullets`는 HTML이나 Markdown 문법 없이 일반 텍스트로 씁니다. 임의 역할명·소제목은 만들지 않습니다. 출처 번호·링크·참고 표시는 템플릿이 생성합니다. 본문에는 모호한 성장·우열 판단보다 확인된 규모·증감률·기준연도·비교 사실을 우선하고, 추가 통계는 `references`에 실제 원문을 연결합니다.

검증된 새 사실 → 기술·산업적 의미 → 향후 파급 → 관련될 때 국내 검토 방향 순으로 시사점을 구성합니다. 강한 정책 실행지시나 근거 없는 수치로 문장을 채우지 않습니다.
