# 원고 생성 자동화 프롬프트

자동화 일정: 09:30 KST, 미완성 시 10:30·11:30 보충. 2026-10-07부터 적용.

Daily Desk의 AI반도체 일일 브리핑 원고를 검증해 GitHub에 저장하라. 이 작업은 원고 생성만 담당한다. 이메일·Gmail 발송, PDF 생성, HTML 디자인 변경은 하지 않는다. 별도 유료 AI API를 호출하지 않는다.

대상은 연결된 GitHub dhkim-0711/daily-desk 저장소 main이다. 매 실행 시 먼저 mail/EDITORIAL_GUIDELINES.md와 mail/GENERATION_CONTRACT.md의 현재 본문을 읽고 그대로 따른다. 기준일은 실행 시점 Asia/Seoul 날짜, 마감은 해당 날짜 09:30 KST, 2026-10-06부터 수집기는 최근 72시간을 확보하고, 원고는 전일 09:30 초과~당일 09:30 이하 신규 보도를 우선한다. 부족 시 마감 전 48시간 이내 미게재 사건만 보완한다. 실제 수집시각과 사건 최초 발표일을 구분한다. 보충 실행도 마감을 바꾸지 않는다.

중복 방지: briefings/state/YYYY-MM-DD.json이 sending/sent/uncertain이면 원고를 변경하지 않고 종료한다. briefings/ready/YYYY-MM-DD.json이 있으면 내용을 읽고 규약상 유효한 완성본인 경우 종료한다. 기존 원고가 무효이고 발송 시도 기록이 없다면 실제 최신 SHA로 수정한다. 유효한 기존 원고를 새로 재작성하지 않는다.

자료는 docs/data/archive/index.json 및 관련 월 docs/data/archive/YYYY-MM.json(월 경계는 두 달)에서 읽는다. firstSeenAt과 publishedAt을 구분하고 실제 수집시각을 collected_at에 기록한다. 수집시각 불명확 시 실제 수집 기록·Git 커밋 등 근거를 확인한다. 09:30 이후 처음 발표된 정보는 다음 날로 넘긴다. 마감 전에 공개됐으나 늦게 수집된 보도는 누락 복구 검증을 거쳐 후보에 포함한다. dashboard.json의 제한된 최신 목록과 규칙 기반 policyIdeas/review/weeklyIssueInsights를 분석 결과로 재사용하지 않는다.

6개 독립 이슈를 원칙으로 AI반도체 산업·생태계 중심에서 선정한다. 기존 6건과 구별되는 중요한 분야·쟁점·산업 변화를 더할 때만 7건으로 확대한다. 다섯 영역별 추가 검색·공식 발표 및 대체 공개 원문 확인을 완료했으나 검증 가능한 중요 이슈가 부족하면 4~5건을 허용하며, 4건 미만이면 오래된 기사나 범용 AI 뉴스로 채우지 않는다. 최종 기사 모두 공개 원문 전문 또는 핵심 사실을 충분히 확인할 수 있는 공개 본문을 읽는다. 유료벽이면 공개 공식자료·신뢰할 수 있는 재배포본으로 교차확인하고 불충분하면 제외한다. RSS 제목·summary·검색결과 한두 줄로 주요 내용을 쓰지 않는다. 기업 주장·언론 인용·애널리스트 추정·확정 사실을 구분하고 수치와 출처를 만들지 않는다.

국내 NPU, 국내 정책·사업화·수요처, 글로벌 가속기, 운영 SW, 메모리·패키징·인프라의 다섯 영역을 각각 점검한 뒤 후보를 비교한다. 국내외·분야별 할당량은 두지 않는다. 기업 인지도·기사 언어·보도량·수집 score 대신 새 사실과 산업 관련성·파급·국내 생태계 의미를 판단한다. 같은 기업집단 중심 기사가 2건 이상이면 독립성과 다른 후보 대비 중요성을 재검토한다. 2026-09-30부터 selection_audit에 영역별 점검 결과, 기사별 선정 이유, 실제 제외 후보의 제목·URL·이유, 기사 수 사유, 기업 반복 검토 결과를 기록한다. 이 기록은 독자용 본문에 쓰지 않는다. 기록을 채우려고 후보·근거를 만들지 않으며 세부 형식은 GENERATION_CONTRACT.md를 따른다.

주요 내용과 시사점은 각 2~3문장. 시사점은 기술 전문가와 한국 정책수립자 관점을 내부적으로 함께 적용하되 관점 라벨을 표시하지 않는다. 기사상 기술·산업 변화→향후 전망·파급→직접 연관될 경우 국내 산업경쟁력·성장동력 관점의 검토 방향 정도로 제안한다. 과도한 확신·정책 실행지시를 피한다. 구체적 사실·규모·증감·기준연도를 우선하고 외부 통계·연구·전망을 추가 인용한 때만 references에 실제 자료명·기관·발행일·URL을 기록한다. 기사 자체 요약에 불필요한 참고를 넣지 않는다. 전체 규정은 EDITORIAL_GUIDELINES.md를 따른다.

완성 파일은 briefings/ready/YYYY-MM-DD.json이다. schema_version=1,status=ready,date,cutoff_at,window_start,created_at,summary_groups,articles,selection_audit를 담는다. summary_groups는 기사번호1~2개와 개조식2문장으로 구성하고 모든 번호가 정확히1회 등장한다. articles는 number,title,category,collected_at,original_published_at,original_url,main_points,implications,sources 및 필요 시 references를 담는다. sources는 실제 title,publisher,published_at,url,verification(full_text/public_primary/public_reprint),verified_at을 담는다. 시간 미상이면 published_at을 YYYY-MM-DD로 보존하고 시각을 지어내지 않는다. 날짜만 알려진 당일·전일 출처/참고는 available_before_cutoff=true와 실제 cutoff_evidence를 필수 기록한다. 처음 보는 파일 규약이 다르면 저장소의 현재 규약을 우선한다.

전체 원고를 완성하고 모든 필드를 검사한 다음 단일 파일 생성/갱신 호출로 원자적으로 저장한다. 실행 도구가 있으면 mail/render.py --input 원고.json --validate-only로도 검사한다. ready 경로에는 중간본·예제를 저장하지 않는다. JSON 안에 HTML/Markdown, 개인 메모, 이메일 주소·인증정보나 원문 전문을 넣지 않는다. 기사 부족/접근 제한/검증 실패/저장 실패는 사유를 명확히 보고하고 완료를 주장하지 않는다.

저장 성공 시 파일의 실제 GitHub 링크와 확인된 단계만 보고한다. 원고 검사까지 통과했으면 '원고 검증·저장 완료, GitHub 제작 및 GPT 발송 대기', 검증을 실행하지 못했으면 '원고 저장 완료·제작 검증 대기'로 구분한다. 발송 완료를 주장하지 않는다. GitHub는 고정 HTML/PDF를 briefings/rendered/YYYY-MM-DD.json으로 제작한다. 별도 GPT 발송 작업이 같은 날 09:50 이후 기존 Gmail 연결로 발신함 확인·중복 방지·발송을 담당한다. 원고 생성 작업은 Gmail 발송을 호출하지 않는다.

정부·지자체 NPU 후보를 필수 검토하라. 중앙부처와 광역·기초지자체·지방의회·공공기관·테크노파크·지역 진흥기관의 NPU 정책, 국비·지방비, 도입·구매·조달, 실증센터·테스트베드·데이터센터, R&D·기업지원·공모 및 집행 지연·축소·취소를 각각 확인한다. 지역 언론과 종합 예산·국비 확보 기사도 본문에 NPU 사업이 있으면 검토하며 제목에 NPU나 기업명이 없다는 이유로 제외하지 않는다. 아카이브 후보를 먼저 확인하고 누락 가능성은 지역명·기관명과 NPU·AI반도체·인공지능반도체·국비·예산·실증·도입·조달을 조합한 공개 원문 조사로 보완한다. 72시간 수집·24시간 신규 보도 우선·48시간 미게재 보완 기준과 09:30 마감·실제 수집시각 근거를 유지한다. 가능한 공식 보도자료·공고·예산자료와 대조하고 제안·건의/정부안 반영/의회 확정/공모·선정/계약·구축/운영·성과를 구분한다. 지역 전체 국비 목표나 여러 사업 총액을 NPU 개별 예산으로 쓰지 않으며 미공개 금액·물량을 추정하지 않는다. 보도량·기업 규모보다 국내 NPU 수요·실증·사업화의 실제 변화를 평가한다. 실제 조사 범위와 결과, 후보 없음·접근 실패·미확인은 selection_audit.coverage.domestic_policy_demand.note에 구분해 남긴다. 의무 기사 할당량은 두지 않고 기존 기본 6건·최대 7건 기준을 따른다.


[제작 단계 연결 검사·오류 복구]
ready 파일 존재 또는 status=ready만으로 완성·유효 판정하지 않는다. 원고 저장 전에 실행 환경이 있으면 저장소의 현재 mail/render.py --input 원고.json --validate-only를 실행하여 성공을 확인한다. 같은 original_url을 가진 두 이슈는 기본적으로 중복 오류이며, 종합기사에 포함된 독립 사건을 각각 별도 공개 원문으로 검증한 경우에만 현재 GENERATION_CONTRACT.md의 selection_audit.shared_original_reviews 규약으로 독립성 근거를 기록한다. 검사 통과를 위해 실제 original_url·collected_at·original_published_at을 바꾸거나 삭제하지 않는다. 검증 출처가 같거나 같은 사건이면 통합 또는 제외한다.
기존 ready가 있지만 rendered가 없으면 실제 원고 검증과 당일 제작 작업 결과를 확인한다. GitHub Actions 조회는 github_fetch의 https://api.github.com/repos/dhkim-0711/daily-desk/actions/runs?per_page=30 을 사용하고 path가 .github/workflows/send-daily-briefing.yml인 당일 실행의 jobs/logs를 확인한다. 실패한 검증은 발송 시도 기록이 없는 경우 현재 규약에 맞게 원고를 보완한다. 검증 실행 없이 저장만 성공한 경우 최종 상태는 '원고 저장 완료·제작 검증 대기'로 표시하고, 검증 실패를 단순 발송 대기로 표현하지 않는다. 수정 불가·도구 미제공·권한 오류는 구체적으로 보고한다.

[2026-10-06부터 수집·선정 보완 필수]
저장소 현재 규약을 우선한다. 최신 체크아웃에서 python mail/candidates.py --date YYYY-MM-DD를 실행해 전체 아카이브 후보, 최근 14일 원고, 수집 상태를 읽는다. 실행할 수 없으면 같은 자료를 GitHub에서 직접 읽는다. docs/data/archive/index.json에서 최근 기간에 걸친 모든 월 파일을 읽고 docs/data/collection/YYYY-MM-DD.json의 source별 failed/empty/ok를 구분한다. 화면용 180건 목록을 조사 범위로 삼지 않는다. 수집기 전체 후보 저장은 상한이 없으며 점수는 중요도나 최종 선정 기준이 아니다.
최근 24시간 신규 보도를 우선하고 부족 시 48시간 이내 미게재 사건만 보완한다. 최초 수집시각은 실제 시각을 보존한다. 마감 전 72시간부터 원고 작성 시점까지의 후보를 읽되, 09:30 이후 처음 발표된 사실은 다음 날로 넘긴다. 늦게 수집한 마감 전 보도는 누락 복구 규약으로 검증한다. 종합기사의 발행일로 오래된 계약·발표를 신규 사건으로 만들지 않는다. event_first_published_at과 event_evidence_url로 사건/실질적 추가 사실의 공개일을 검증한다.
최근 14일 briefings/ready의 모든 실제 원고를 제목·주요 사실·출처까지 읽고 사건 단위 중복을 비교한다. 제목·매체·URL·언어 변경은 새 사건이 아니다. 과거 같은 사건은 추가 금액·확정 일정·운영 성과 등 실질적인 새 사실과 검증 출처가 있을 때만 후속 선정한다. 같은 종합기사 속 다른 계약은 별도 공개 원문과 독립성 기록을 갖춘 경우에만 분리한다. helper의 exact_history_matches에 없다는 이유만으로 신규 판정하지 않는다.
기사별 event_id,event_first_published_at,event_evidence_url,selection_tier(primary/supplement), 필요 시 recency_evidence를 작성한다. selection_audit에는 candidate_counts(discovered,time_eligible,independent_events,verified,selected,basis), history_review(start_date,end_date,checked_dates,note), 기사별 event_reviews(article_number,result,previous_editions,note 및 후속 new_fact,evidence_url)를 현재 규약에 맞게 기록한다. 모든 수치·확인 기록은 실제 결과만 기록한다.
4~5건 마감 또는 48시간 보완 전 다섯 영역의 추가 검색과 공식 발표·공고 확인, 유료벽/접근 제한 후보의 대체 공개 출처 조사를 마치고 additional_search를 기록한다. 국내 NPU·정부/지역기관은 공식 뉴스룸·사업공고도 직접 확인한다. 운영 SW·HBM·패키징·인터커넥트 검색을 빠뜨리지 않는다. 조회 실패/권한 오류/미확인을 후보 없음으로 바꾸지 않는다. 추가 조사가 끝나지 않았으면 조사 미완료라고 보고한다. 기본 6건·최대 7건을 유지하며 오래된 기사·중복·일반 AI 기사로 수를 채우지 않는다.
메일·PDF 본문에는 내부 감사 기록을 넣지 않는다. 원고 저장 전 최신 history를 포함한 체크아웃에서 mail/render.py --validate-only 검사를 통과시킨다. 과거 발송본은 수정·재발송하지 않는다.
